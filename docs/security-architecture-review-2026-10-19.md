# 보안 센터 구조·효율 점검 (2026-10-19)

## 운영 흐름

현황은 서버·수집에서 확인할 일, 탐지 대응함, 수집 연결, 최근 신호와 운영 변경을 보여 준다. 신호 수를 공격 횟수·성공률로 표현하지 않는다. 데스크톱에서는 좌측 작업 메뉴를 유지하고 모바일에서는 다섯 작업 영역을 모두 노출한다.

탐지·대응은 목록과 선택한 상세를 분리한다. IP·출처·위험도·상태로 검색하고 근거 → 현재 웹 IP 정책 → 관련 기록 → 판단·조치 → 이력을 확인한다. 선택은 URL에 남아 완료 처리 후에도 같은 건을 볼 수 있다. 목록 20개의 폼·이력을 모두 렌더링하던 방식에서 선택한 건의 폼 하나·이력 조회 하나로 변경했다. 선택 전에는 대응 폼을 만들지 않는다.

IP 관리는 활성 차단·허용과 변경 이력을 유지한다. 보호 점검은 남은 위험 → 수집 상태 → 적용 방어를 먼저 보여 주고 규칙·보관 한도·수집 구조·원본 서버 설정은 필요할 때 펼친다. 수집 연결은 취약점 검사 통과 표시가 아니다.

## 수집·탐지·저장 구조

- 웹 요청은 nginx → 접근·요청 검증 → 정제한 신호 → SQLite 집계 → 탐지 대응함으로 연결된다. 정상 요청을 매번 기록하지 않는다. IP 규칙·관리자 권한·로그인 한도·nonce는 캐시하지 않아 변경과 만료가 바로 반영된다.
- nginx는 새 로그를 256KB 이내로 읽고 JSON 해석을 쓰기 잠금 전에 끝낸다. 트랜잭션 안에서 공유 커서가 그대로인지 다시 확인한 뒤 집계한다. 다른 프로세스가 먼저 처리한 배치는 버린다. 유휴 확인·짧은 미완성 행은 DB에 쓰지 않는다. 대기량이 256KB 이상이면 1초, 그 외는 10초마다 확인한다.
- nginx 마지막 성공 확인·오류·처리 대기량은 프로세스 메모리에서 관리한다. 커서 갱신 시각을 수집 건강 상태로 오인하지 않는다. 빈 로그도 확인에 성공하면 연결 상태이며 파일 오류·45초 이상 지연은 별도 상태다. 독립적인 외부 가용성 감시는 아니다.
- SSH·방화벽 파일은 기존 root 소유 읽기 전용 수집기가 1분마다 만들고 앱이 15초마다 확인한다. 검증한 JSON은 inode·크기·나노초 수정/변경 시각이 같은 동안 재사용한다. 최대 4개·파일당 128KB이며 최신성은 캐시 적중 때도 다시 판단한다. 교체·잘못된 내용·미래 시각·3분 지연은 기존 검증을 유지한다.
- 변하지 않은 SSH 세대는 읽기 조회 후 반환한다. 새 세대는 트랜잭션 안에서 재검사하고 이벤트 해시를 공유해 겹치는 프로세스의 중복 집계를 막는다. 신선한 파일이 있어도 DB 반영 실패는 수집 장애로 표시한다.
- 기록 실패는 원래의 접근 거절 결과를 바꾸지 않는다. 오류 출력은 1분에 한 번으로 제한하며 최근 실패를 화면에도 표시한다.
- 스키마 6은 IP/종류별 이벤트 조회, 대응 이력 FK/정렬, SSH 해시 정렬, 만료 정리에 쓰는 인덱스만 추가한다. 기존 테이블·보관 한도·권한 경계를 유지한다. 인덱스는 쓰기 비용과 DB·마이그레이션 백업 크기를 증가시킬 수 있다.

## 격리 측정

Node v24.19.0, 임시 SQLite와 가짜 수집 파일을 사용한 같은 실행 환경의 변경 전/후 측정이다. 운영 서버 부하 실측이 아니다. `npm run bench:security`로 현재 구조를 다시 측정한다. 시간은 환경에 따라 달라지며 무작위 시간 임계치를 CI에 두지 않는다.

| 항목 | 이전 | 변경 후 |
| --- | ---: | ---: |
| 변화 없는 nginx/SSH 각 100회 확인의 쓰기 트랜잭션 | 200 | 0 |
| 같은 확인에서 DB 쓰기 호출 | 100 | 0 |
| 같은 확인 + 화면 조회에서 SSH JSON 파일 읽기 | 200 | 0 (최초 검증 후) |
| 1만 행 중 특정 IP 조회 100회 | 233.29ms | 1.71ms |
| 해당 조회 실행 계획 | 시간 인덱스 후 IP 필터 | IP·시간 인덱스 검색 |

유휴 루프 전체 시간은 10.46ms → 9.23ms였다. 핵심 효과는 반복적인 쓰기 잠금·WAL 갱신·파일 파싱 제거다. 파일 stat과 공유 커서의 읽기 조회는 계속한다. 조회 수치는 특정 필터의 측정이며 전체 서비스가 같은 배수로 빨라졌다는 뜻은 아니다. 회귀 테스트는 유휴 쓰기 0회, 캐시 최신성·교체 검증, 두 프로세스의 중복 소비 방지, 권한과 인덱스 검색을 검증한다.

## 지금까지의 보안 점검

| 경계 | 적용·검증한 내용 | 남은 한계 |
| --- | --- | --- |
| 인증·권한 | DB 관리자 재검사, 서명·고정 HTTPS origin, IP 요청 한도, OAuth 상태·nonce 1회 | 공유 IP 오탐, 외부 Google 전체 로그인은 별도 계정 검증 필요 |
| HTTP·브라우저 | 출처/메서드·인코딩 민감 경로 차단, CSP nonce, 첨부 경로·용량·다운로드 권한 | 학생 코드·본문·쿼리 값은 검사하지 않음 |
| 반복 탐지 | 경로·인증·권한·404/429·SSH 실패 집계, 탐지기와 화면의 정책 정의 통합 | 분산·저속 탐색과 모든 SSH 로그 형식은 탐지하지 못함 |
| 대응 | 민감 경로만 짧은 자동 웹 차단, 수동 차단·허용·해제·자기 차단 방지, 검토·재발 이력 | 웹 IP 차단은 SSH·DNS·포트 스캔 방어가 아님 |
| 기록 | 쿼리/본문/토큰·SSH 계정명/키/원문 제외, 기간·행 수 한도 | root 침해 시 같은 서버의 로그도 변조 가능 |
| 서버 | 포트·SSH 설정·패키지·sudo·INPUT 규칙 관측, 무효 차단 순서 표시 | 전체 무암호 sudo/앱·러너 계정 공유는 별도 구조 이전 필요 |

추가로 로그인하지 않은 반복 운영자 접근도 권한 신호에 연결했다. 한 OAuth 재사용 응답을 재사용과 일반 로그인 실패로 두 번 집계하지 않는다. 자동 차단 범위는 넓히지 않았다.

외부 Nmap의 DNS 응답과 내부 리스너의 불일치, OCI·NAT·FORWARD·컨테이너·사용자 체인, 모든 포트 스캔·볼륨 DDoS·침해 성공은 이 센터만으로 결론 내리지 않는다. SSH·방화벽을 자동 변경하거나 sudo를 회수하지 않는다. 남은 위험은 관측 시각과 함께 표시한다.

기준: [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html), [SQLite Query Planning](https://www.sqlite.org/queryplanner.html), [SQLite Foreign Keys](https://www.sqlite.org/foreignkeys.html), 설치된 Next.js의 Server Actions/refresh 가이드. 저장소 회귀·HTTP·브라우저 확인 및 CI로 동작을 검증한다.
