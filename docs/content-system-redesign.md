# 콘텐츠 저장/관리 시스템 개선 기획

상태: **기획안 — 아직 구현하지 않음.** 검토 후 진행 여부를 결정하기 위한 문서.

## 1. 왜 지금 바꿔야 하는가

현재 8주차 분량 콘텐츠는 `src/content/weeks/week{1..8}.ts` 8개 파일에 들어있다. 각 파일은
메타데이터(제목/난이도/목표 등)와 `conceptsMd`/`practiceMd`/`assignmentMd`라는 세 개의
거대한 마크다운 문자열, 그리고 `quiz`/`worksheet` 배열을 한 파일 안에 전부 담고 있다.
이 구조에서 이번 세션 동안 실제로 반복해서 발생한 문제들:

- **백틱/백슬래시 이스케이프 버그.** 마크다운 본문이 JS 템플릿 리터럴(백틱 문자열) 안에
  들어있다 보니, 본문에 인라인 코드(`` `code` ``)나 LaTeX 백슬래시를 쓸 때마다 이스케이프를
  틀리면 파일이 깨진다. 실제로 이번 세션에서 3회 이상 이 문제로 빌드가 깨졌다.
- **거대한 단일 파일.** 한 주차 파일이 200~400줄이 넘는 문자열 덩어리라, "3주차 2.4절만
  고치고 싶다" 같은 작은 수정도 파일 전체를 열어야 하고, git diff도 커서 리뷰하기 어렵다.
- **퀴즈-정답 분리 저장.** 퀴즈 문항은 `weekN.ts`에, 정답은 `quizAnswers.ts`에 따로 있어
  둘을 계속 손으로 동기화해야 했다(이번 세션에서 id 기반 구조로 1차 개선했지만, 여전히
  파일이 2개로 나뉘어 있다).
- **비개발자가 편집하기 어렵다.** TypeScript 문법과 이스케이프 규칙을 모르면 본문 한 줄도
  안전하게 못 고친다. 분량이 늘어나 여러 사람이 콘텐츠를 나눠 쓰게 되면 이 장벽이 병목이 된다.

지금은 8주차라 버틸 만하지만, "훨씬 더 많은 분량"으로 늘리려는 지금이 구조를 바꾸기 가장
싼 시점이다(나중에 늘어난 뒤 바꾸면 마이그레이션 비용도 같이 커진다).

## 2. 목표

1. 마크다운 본문을 **진짜 `.md` 파일**로 분리해 이스케이프 문제를 원천적으로 없앤다.
2. 콘텐츠를 **더 작은 단위**로 쪼개 diff를 작게 만들고, 부분 수정을 쉽게 한다.
3. 퀴즈 문항과 정답을 **하나의 파일**에서 관리해 동기화 문제를 완전히 없앤다.
4. TypeScript 타입 검사를 잃는 대신 **런타임 스키마 검증**으로 안전망을 유지·강화한다.
5. **기존 렌더링 파이프라인은 그대로 둔다** — `MarkdownBlocks.tsx`, 커스텀 마크다운 문법
   (`\`\`\`math`, `\`\`\`image`, `:::info`, `[[diagram:id]]`), KaTeX, `validate-content.ts`는
   전부 지금 그대로 재사용한다. 바뀌는 것은 **콘텐츠가 어디에, 어떤 형태로 저장되는가**뿐이다.

## 3. 제안하는 구조

```
content/                          # 순수 데이터. 코드가 아니라 "콘텐츠 저장소"
  weeks/
    week01/
      meta.yaml                   # 제목/부제/난이도/목표/키워드/학습순서/마감안내/참고자료
      concepts.md                 # "2. 핵심 개념" 본문 (지금의 conceptsMd)
      practice.md                 # "3. 실습" 본문 (지금의 practiceMd)
      assignment.md               # "6. 과제" 본문 (지금의 assignmentMd)
      quiz.yaml                   # [{ id, question, answer, explanation? }] — 정답까지 한 파일에
      worksheet.yaml              # [{ label, hint }]
    week02/
      ...
    week24/                       # 두 자리 zero-padding으로 24주+ 확장 대비
      ...

src/content/                      # 코드. "content/의 데이터를 읽어서 WeekMeta로 변환"
  loadWeek.ts                     # fs로 content/weeks/weekNN/*를 읽어 WeekMeta[] 생성
  schema.ts                       # zod 스키마 (meta.yaml/quiz.yaml 형태 검증)
  markdown.ts                     # 기존 파서 그대로 유지
  types.ts                        # WeekMeta 등 타입 그대로 유지
```

- **week 번호는 2자리 zero-pad(`week01`)**로 통일 — 지금처럼 `week1`~`week8`이면 9주차부터
  파일 목록 정렬이 깨진다.
- **퀴즈 파일 하나로 통합**: 지금처럼 `weekN.ts`(문항)과 `quizAnswers.ts`(정답)로 나뉘지
  않고, `week01/quiz.yaml` 한 파일 안에 `{ id: "w1-q1", question: "...", answer: "..." }`
  형태로 같이 둔다. 파일 하나만 보면 문항과 정답이 바로 옆에 있어 리뷰가 쉽고, 애초에
  "따로 있는 두 배열을 동기화"할 필요 자체가 없어진다. (운영자 전용 정답 페이지는
  지금처럼 로그인/권한 체크로 노출을 막으면 된다 — 파일이 합쳐져도 접근 제어는 별개 문제.)
- **메타데이터는 YAML**: `title`, `quiz`, `worksheet` 같은 구조화된 데이터는 YAML로 —
  JSON보다 여러 줄 문자열/한글 텍스트를 다루기 편하고, 주석도 달 수 있다. 새 의존성은
  `js-yaml` 하나만 추가하면 된다(수십 KB짜리, 매우 표준적인 패키지).
- **본문은 순수 마크다운**: `.md` 파일 안에는 정말 마크다운만 있고 프런트매터도 없다 —
  메타데이터는 `meta.yaml`에 이미 있으니 본문 파일은 순수하게 유지해서 아무 마크다운
  에디터로 열어도 깨지는 것 없이 그대로 보이게 한다.

## 4. 로딩 방식 (컴포넌트/렌더링은 무변경)

`src/content/loadWeek.ts`가 빌드/서버 시작 시 `content/weeks/*` 디렉터리를 순회하며 각
`meta.yaml` + `*.md` + `quiz.yaml` + `worksheet.yaml`을 읽어 지금과 똑같은 `WeekMeta` 객체
배열을 만든다. `WEEKS`를 소비하는 모든 곳(`src/app/weeks/[slug]/page.tsx`,
`src/app/operator/quiz-answers/page.tsx` 등)은 **코드를 한 줄도 바꿀 필요가 없다** —
지금도 `import { WEEKS } from "@/content/weeks"`로 배열을 가져다 쓸 뿐, 그 배열이
`.ts` 리터럴에서 나왔는지 `.md`/`.yaml` 파일에서 나왔는지는 신경 쓰지 않기 때문이다.
`parseMarkdown`에 이미 있는 캐시(`Map`)도 그대로 유효하다.

## 5. 검증 강화 (`validate-content.ts` 확장)

TS 리터럴에서 파일로 옮기면 컴파일타임 타입 체크를 잃는 대신, 이미 만들어둔 검증
스크립트에 **zod 스키마 검사**를 추가해 그 이상의 안전망을 확보한다:

- `meta.yaml`/`quiz.yaml`/`worksheet.yaml`이 정확한 필드와 타입을 갖췄는지 (zod)
- 지금 이미 하고 있는 것: 퀴즈 id 정합성, LaTeX 유효성, 이미지 파일 존재/종횡비, 날것 수식 탐지
- 추가로: 파일이 존재해야 하는데 없는 경우(`meta.yaml`은 있는데 `quiz.yaml`이 없음 등)를
  주차별로 명확히 짚어주는 오류 메시지

`npm run validate:content`와 CI 연동은 지금 그대로 유지, 스키마 위반도 같은 방식으로
빌드를 막는다.

## 6. 마이그레이션 방법

내용을 새로 쓰는 게 아니라 **지금 있는 텍스트를 그대로 옮기는 기계적 작업**이라 리스크가
낮다. 이번 세션에서 퀴즈 id 마이그레이션에 썼던 것과 같은 방식 — TypeScript AST로 각
`weekN.ts`의 `conceptsMd`/`practiceMd`/`assignmentMd`/`quiz`/`worksheet` 리터럴의 정확한
원문을 추출해 새 파일 구조로 그대로 옮겨 쓰는 1회성 스크립트를 짠다. 사람이 내용을
다시 타이핑하지 않으므로 오탈자/누락 위험이 거의 없고, 옮긴 뒤 `validate-content.ts` +
기존 8주차 원문과의 diff 비교로 "글자 하나도 안 바뀌었는지"까지 기계적으로 검증할 수 있다.

## 7. 트레이드오프 정리

| | 지금 (`.ts` 리터럴) | 제안 (`.md`+`.yaml`) |
|---|---|---|
| 이스케이프 버그 위험 | 있음 (반복 발생) | 없음 |
| 컴파일타임 타입 체크 | 있음 | 없음 → zod 런타임 검증으로 대체 |
| 비개발자 편집 난이도 | 높음 | 낮음 (일반 마크다운/YAML) |
| diff 크기 | 큼 (파일 하나에 다 있음) | 작음 (섹션별 파일 분리) |
| 새 의존성 | 없음 | `js-yaml` 1개 |
| 마이그레이션 비용 | — | 1회성, 기계적, 검증 가능 |
| 렌더링/URL/기존 문법 | — | **무변경** |

## 8. 단계적 진행 제안

이 문서는 설계만 다룬다. 진행하기로 하면 아래 순서를 제안한다(각 단계는 별도로 검토·승인
후 진행):

1. `js-yaml` 추가, `schema.ts`(zod) 작성, `loadWeek.ts` 작성 — **기존 8주차는 아직 안 건드림**
2. `week01` 하나만 새 구조로 마이그레이션해 파일럿 검증 (렌더링 결과가 기존과 100% 동일한지 diff)
3. 파일럿이 문제없으면 나머지 week02~08을 같은 스크립트로 일괄 마이그레이션
4. 기존 `weekN.ts`/`quizAnswers.ts` 삭제, `validate-content.ts`에 스키마 검사 추가
5. (선택, 더 나중) 운영자 전용 웹 UI에서 이 파일들을 직접 읽고 저장하는 경량 편집기 —
   git 커밋 없이도 콘텐츠 수정이 가능해짐. 지금 단계에서는 범위 밖으로 두고 아이디어만 남김.

## 9. 지금 당장 하지 않는 이유가 될 수 있는 것들

- 8주차 정도 분량에서는 지금 구조도 "불편하지만 버틸 만한" 수준이다 — 마이그레이션이
  급하지 않다면 콘텐츠를 먼저 늘리고 나중에 한 번에 옮겨도 된다(다만 늘어난 만큼 옮길
  텍스트도 늘어나므로 비용이 커질 뿐, 리스크가 커지진 않는다 — 기계적 스크립트이므로).
- `js-yaml`이라는 새 의존성이 부담스럽다면, YAML 대신 지금 `\`\`\`image` 펜스에 쓰는 것과
  같은 "key: value 줄 단위" 커스텀 프런트매터 파서를 하나 더 만들어 의존성 0개를 유지하는
  대안도 가능하다 — 다만 여러 줄 문자열/리스트 표현력이 YAML보다 떨어진다.
